**Dana (QA Engineer):** "The test infrastructure was set up correctly from the start. Backend uses Node's built-in `--test` runner, frontend uses Vitest with jsdom. Both exit 0 even with no test files initially — the `--passWithNoTests` fix in 1.1 was a small but critical catch."

**Elena (Junior Dev):** "The `createDb(url)` factory in Story 1.4 was a smart deviation from the original plan. A top-level module export would have called `postgres()` before `@fastify/env` loaded the connection string. The factory avoids the ES module hoisting bug entirely."

**Winston (Architect):** "Agreed. That's the kind of deviation you want — it's functionally superior to the spec. The dev recognized the problem at implementation time and solved it correctly."

**Alice (Product Owner):** "From a product perspective, the Docker Compose story delivers developer experience. `docker compose up` and you have everything running — postgres, backend, frontend with nginx. No local Node install required for demos. That matters for onboarding."

### What Didn't Go Well

**Bob (Scrum Master):** "Now the harder conversation. Where did we struggle?"

**Charlie (Senior Dev):** "The import extension situation in Story 1.2. Node 22.19 does not correctly remap `.js` imports to `.ts` files despite the documentation suggesting it should. We had to switch all imports to `.ts` extensions and add `allowImportingTsExtensions` and `rewriteRelativeImportExtensions` to `tsconfig.json`. It works, but it's a deviation from how most TypeScript + Node projects operate."

**Winston (Architect):** "The architecture spec assumed `.js` extensions would work at runtime with TypeScript strip-types. That assumption was wrong for Node 22.19. The fix is correct, but it means every subsequent story's import convention follows a non-standard pattern. If we upgrade Node later, we may want to revisit."

**Dana (QA Engineer):** "Story 1.5 has zero automated tests. The Docker integration was verified manually — `curl` against health and frontend endpoints. That's acceptable for an infrastructure story, but it means there's no regression safety net if someone changes `docker-compose.yml` or the Dockerfiles."

**Charlie (Senior Dev):** "The `localhost` vs `127.0.0.1` issue in the Docker healthcheck is a good example of environment-specific surprises. Alpine's `wget` resolves `localhost` to IPv6 first, but Fastify binds IPv4 only. Small issue, but it took debugging time."

**Elena (Junior Dev):** "There's no `.dockerignore` in either the backend or frontend directories. If you have a local `node_modules`, `COPY . .` pulls it into the build context. It doesn't break the build — the multi-stage Dockerfile does a clean `npm install` — but it makes the build context larger and slower than necessary."

### Key Insights

1. **The `app.ts` factory pattern is a force multiplier.** Every backend test in every subsequent epic benefits from being able to create a Fastify instance without binding a port. This was the most impactful decision in Epic 1.

2. **Node 22 + TypeScript import extensions require explicit configuration.** The `.ts` import convention with `allowImportingTsExtensions` works but is non-standard. This should be documented as a project convention so new contributors don't revert it.

3. **Database factory (`createDb(url)`) correctly avoids ES module hoisting.** Top-level `postgres()` calls execute before `@fastify/env` populates environment variables. The factory pattern defers connection creation to plugin registration time.

4. **Docker Compose healthchecks need IPv4 awareness.** Alpine containers resolve `localhost` to `::1` first. Always use `127.0.0.1` in healthcheck commands when the server binds IPv4.

5. **Frontend stubs (`api.ts`, `identity.ts`) are intentional debt.** They throw at runtime, which is correct — they're placeholders until Story 2.3. The throw-on-use pattern prevents silent misuse.

### Team Agreements

- **`app.ts` factory pattern** is mandatory — no story may call `listen()` inside `app.ts`
- **Import extensions** use `.ts` in backend source; `rewriteRelativeImportExtensions` handles compilation
- **Docker healthchecks** use `127.0.0.1` instead of `localhost` for IPv4 compatibility
- **Every scaffolding story** must verify that both `npm run test:backend` and `npm run test:frontend` exit 0 before marking done
