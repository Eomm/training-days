### What Went Well

**Bob (Scrum Master):** "Let's start with wins."

**Winston (Architect):** "The three-story decomposition was clean. 2.1 creates the identity on the server. 2.2 enforces it on every request. 2.3 wires it into the client. Each story has a single responsibility, and the boundary between them is the HTTP contract — `POST /guest` and the `X-User-Id` header."

**Charlie (Senior Dev):** "The `createDb(url)` factory pattern from Epic 1 paid off immediately. Story 2.1 needed to run tests against a real `users` table insert, and the factory meant we could inject a test database URL in `before()` hooks without fighting ES module hoisting. That Epic 1 decision saved debugging time in every backend story."

**Dana (QA Engineer):** "Test growth is strong — 6 to 25 across the epic. The backend went from 4 tests to 12, and the frontend went from 2 to 13. More importantly, the test patterns established here are reusable. The `app.inject()` pattern for backend integration tests and the `vi.stubGlobal('fetch', ...)` pattern for frontend tests will carry through Epic 3 and beyond."

**Elena (Junior Dev):** "The `useGuestIdentity` hook in Story 2.3 handles React 18 StrictMode correctly. The cancellation flag (`let cancelled = false`) in the `useEffect` prevents double-initialization when StrictMode re-runs effects. That's a subtle bug that would have been painful to debug later."

**Winston (Architect):** "And the `apiFetch<T>()` wrapper in 2.3 is well-designed. It attaches the `X-User-Id` header conditionally — only when `getUserId()` returns non-null. That means `POST /guest` itself doesn't send the header, which is correct because the header doesn't exist yet at that point."

**Alice (Product Owner):** "From a product perspective, this epic resolves the intentional debt from Epic 1. The `api.ts` and `identity.ts` stubs that threw at runtime are now real implementations. That closes the loop cleanly."

### What Didn't Go Well

**Bob (Scrum Master):** "Now the harder conversation. Where did we struggle?"

**Charlie (Senior Dev):** "Story 2.2 had an unplanned deviation — the `/documentation` route. After registering the global `validateUserIdHook`, Swagger UI stopped working. It returned 400 because the hook requires `X-User-Id` on every route, and Swagger UI routes don't send it. The fix was straightforward — add a prefix exemption — but it wasn't in the original acceptance criteria."

**Winston (Architect):** "That's a planning gap. The AC said 'exempt `/guest` and `/health`' but didn't consider that `/documentation` is a developer-facing route that also needs exemption. The root cause is that the epic treated developer tooling routes as invisible, but the global hook sees all routes."

**Dana (QA Engineer):** "It's a small fix, but it's a pattern risk. If we add more Fastify plugins that register routes — say, a metrics endpoint or a status page — the hook will block those too unless the exempt list is updated. The current approach uses a hardcoded prefix list. That's fine for three routes, but it won't scale."

**Charlie (Senior Dev):** "There's also a testing subtlety in Story 2.2. Tests needed to register a dummy `/test-protected` route before the first `app.inject()` call. If you inject first, Fastify seals the instance and throws `FST_ERR_INSTANCE_ALREADY_LISTENING`. That ordering constraint isn't obvious and cost debugging time."

**Elena (Junior Dev):** "In Story 2.3, the hook was named `useGuestIdentity` instead of `useIdentity` as the epics spec suggested. The architecture document uses `useGuestIdentity`, and architecture is source of truth, so it's correct — but the naming discrepancy between the two documents could confuse a new developer reading the story."

**Bob (Scrum Master):** _to Nearformer_ "The identity flow is working end-to-end, but the global hook exemption pattern and document-level naming inconsistencies surfaced. The `/documentation` fix was quick, but should we consider a more scalable exemption strategy — like a route-level decorator — for future routes? Or is the prefix list sufficient for MVP?"

### Key Insights

1. **Global hooks see all routes, including developer tooling.** Any globally registered `onRequest` hook must account for plugin-registered routes like Swagger UI. An exemption list should be reviewed whenever new Fastify plugins are added.

2. **The `apiFetch<T>()` wrapper centralizes header management.** By conditionally attaching `X-User-Id` based on `getUserId()`, the wrapper ensures consistent header behavior across all API calls without requiring each call site to handle it.

3. **React 18 StrictMode cancellation is essential for initialization hooks.** The `let cancelled = false` pattern in `useGuestIdentity` prevents double `POST /guest` calls during development. This pattern should be applied to any hook that makes one-time setup API calls.

4. **Test ordering matters with Fastify's sealed instance.** Routes must be registered before the first `inject()` call. This constraint should be documented as a testing convention.

5. **Architecture document is source of truth over epics spec.** When naming conflicts arise between the epics breakdown and the architecture document, architecture wins. The `useGuestIdentity` vs `useIdentity` naming was resolved correctly, but the discrepancy itself signals that document alignment should be checked during story creation.

### Team Agreements

- **Hook naming** follows architecture document, not epics spec, when conflicts arise
- **Global `onRequest` hooks** must maintain an up-to-date exempt route list reviewed at plugin registration time
- **Fastify test routes** are registered before the first `inject()` call — document this in test file headers
- **Frontend initialization hooks** use the cancellation flag pattern (`let cancelled = false`) for StrictMode safety
