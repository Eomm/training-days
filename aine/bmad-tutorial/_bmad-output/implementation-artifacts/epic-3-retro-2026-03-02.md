### What Went Well

**Bob (Scrum Master):** "Let's start with wins."

**Winston (Architect):** "The component evolution across the epic was textbook incremental delivery. `TodoList` started as plain `<li>` elements in 3.1, got upgraded to `<TodoItem>` in 3.2, gained a done button in 3.3, and a delete button in 3.4. Each story added exactly one capability without rewriting what came before. The scope boundary tables in each story file made the 'not this story' boundaries explicit."

**Charlie (Senior Dev):** "The three optimistic update patterns are the standout technical achievement. Each mutation type got a pattern tailored to its semantics:

- **addTodo**: prepend with temp UUID → swap with server-confirmed item on success → filter out on error
- **markDone**: save reference → toggle in place → replace with server item → restore on error
- **deleteTodo**: capture full snapshot → filter out → no-op on success → restore snapshot on error

These aren't copy-paste variations — each pattern handles success and failure differently because the data flow is different."

**Dana (QA Engineer):** "The ownership check pattern is consistent across PATCH and DELETE: fetch → check exists (404) → check userId match (403) → proceed. Same pattern, same error shapes, same test structure. That consistency makes the test suite predictable and makes regressions easy to spot."

**Elena (Junior Dev):** "The `quotes.json` implementation exceeded requirements. Architecture spec called for 100+ quotes, and 101 were delivered. Loading them once at module level via `createRequire(import.meta.url)` avoids repeated file reads and sidesteps the Node 22 JSON import assertion deprecation. Clean decision."

**Alice (Product Owner):** "The QuoteModal is a small thing, but it's the product's personality. Marking a task done → seeing an encouraging quote tied to a shadcn Dialog with 'Keep going!' as the dismiss button. That's the kind of detail that turns a utility into an experience."

**Winston (Architect):** "I also want to highlight the `useTodos` hook evolution. It started in 3.1 returning `{ todos, isLoading, error }`. By 3.4 it returns `{ todos, isLoading, error, addTodo, markDone, deleteTodo, quote, clearQuote }`. The hook grew organically across four stories without a refactor boundary. That's a sign the initial API surface was designed with growth in mind."

### What Didn't Go Well

**Bob (Scrum Master):** "Now the harder conversation. Where did we struggle?"

**Charlie (Senior Dev):** "Honestly? Not much. But there's one real issue: the `api.ts` 204 fix in Story 3.4. Without it, every successful DELETE throws a JSON parse error because `response.json()` fails on an empty body. This is marked as a 'critical fix' in the story file — but it shouldn't have been discovered in 3.4. It should have been anticipated in 3.1 when `apiFetch` was authored, or at least when the architecture spec established `204 No Content` for deletes."

**Winston (Architect):** "That's fair. The `apiFetch<T>()` wrapper was written in 2.3 with the assumption that every response has a JSON body. That assumption held through 3.1, 3.2, and 3.3 — all return JSON. But 3.4's DELETE returns 204 with an empty body, which breaks the assumption. The fix is trivial — `if (response.status === 204) return undefined as T` — but the fact that it was discovered at the last story is a planning gap."

**Dana (QA Engineer):** "The good news is that this is the only infrastructure-level fix in the entire epic. And the fix is clean — one line, no side effects. But it reinforces a process point: utility functions like `apiFetch` should be reviewed against all known API response shapes when they're first written, not just the shapes used in the current story."

**Elena (Junior Dev):** "The code review fixes across the epic were all minor — removing unnecessary `as any` casts and adding a `DialogDescription` for Radix UI accessibility. But the `as any` casts appeared in both 3.3 and 3.4, which means the same patterns were introduced twice. A convention note after 3.3's code review would have prevented the reoccurrence in 3.4."

**Bob (Scrum Master):** _to Nearformer_ "This was the smoothest epic so far — zero blockers, zero deviations. The `apiFetch` 204 fix is the only real process gap. Should we add a checklist item for utility function reviews against known API contracts? Or is this level of late discovery acceptable for MVP pace?"

### Key Insights

1. **Three distinct optimistic update patterns, each tailored to its mutation.** Copy-pasting a single optimistic pattern across add/done/delete would have created subtle bugs. The temp-UUID-swap, in-place-toggle, and snapshot-restore patterns each handle success and failure paths correctly for their specific data flow.

2. **Consistent ownership checks reduce cognitive load.** The fetch → 404 → 403 → proceed pattern is identical across PATCH and DELETE. This consistency makes the codebase predictable and test suites uniform.

3. **`createRequire` is the pragmatic ESM JSON loader for Node 22.** It avoids the deprecated `import ... with { type: 'json' }` syntax, avoids `fs.readFileSync` noise, and loads once at module level. This should be the project standard for static JSON data.

4. **Utility functions must be reviewed against all known API contracts.** `apiFetch` was written for JSON responses only and broke on 204 No Content. Reviewing utility signatures against the full API surface at authoring time prevents late-story fixes.

5. **Incremental component evolution works when scope boundaries are explicit.** The scope boundary tables in each story file prevented premature feature addition and made the growth path (`TodoItem`: basic → +onDone → +onDelete) predictable.
